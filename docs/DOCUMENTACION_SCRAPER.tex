\section{Prop\'{o}sito y alcance}

El proyecto construye y mantiene un cat\'{a}logo de eventos culturales de Chile a partir de fuentes p\'{u}blicas: agendas municipales, espacios culturales, universidades, portales sectoriales y tiqueteras. Su objetivo no es copiar una p\'{a}gina completa, sino convertir informaci\'{o}n p\'{u}blica heterog\'{e}nea en registros comparables, trazables y vigentes.

El scraper abarca cuatro responsabilidades:
\begin{enumerate}
  \item descubrir y extraer eventos desde fuentes configuradas;
  \item normalizar fechas, ubicaci\'{o}n, categor\'{i}as, organizador y enlaces;
  \item enriquecer solo los casos necesarios mediante OCR y redacci\'{o}n asistida por IA;
  \item exportar un respaldo local y sincronizar el cat\'{a}logo publicado con Supabase.
\end{enumerate}

No forma parte de este documento el frontend, la autenticaci\'{o}n de usuarios ni el algoritmo de recomendaciones. El scraper alimenta el cat\'{a}logo que dichas capas consumir\'{a}n posteriormente.

\subsection{Principios de dise\~{n}o}

\begin{itemize}
  \item \textbf{Trazabilidad:} cada evento conserva fuente, URL original, URL oficial cuando existe, m\'{e}todo de extracci\'{o}n y momento de captura.
  \item \textbf{Preferencia por datos estructurados:} API, JSON-LD, WordPress REST y tarjetas declarativas se usan antes que OCR o modelos de IA.
  \item \textbf{M\'{i}nima presi\'{o}n sobre los sitios:} se respeta el ritmo por dominio, hay cach\'{e} condicional HTTP y la concurrencia es acotada.
  \item \textbf{Idempotencia:} repetir una ejecuci\'{o}n actualiza registros existentes y evita duplicados mediante identificadores estables y deduplicaci\'{o}n.
  \item \textbf{Resiliencia:} una fuente ca\'{i}da, un afiche ilegible o una respuesta transitoria de NVIDIA no detienen el resto del proceso.
  \item \textbf{Vigencia:} se retiran eventos vencidos y registros ausentes de fuentes completas, respetando supresiones, interacciones y las protecciones de publicaciones manuales.
\end{itemize}

Cada archivo en \texttt{sources/} declara URL, regi\'{o}n, comuna, organizador, conector, categor\'{i}as por defecto, l\'{i}mites de paginaci\'{o}n y, cuando corresponda, metadatos est\'{a}ticos de ubicaci\'{o}n. A\~{n}adir una fuente no exige modificar el archivo principal: primero se intenta configurar un conector existente; solo se crea c\'{o}digo nuevo cuando la estructura no coincide con ninguno.

Las cinco incorporaciones del 27 de octubre de 2026 se comprobaron mediante extracci\'{o}n local de solo lectura, sin NVIDIA ni Supabase. Entregaron 43 fichas vigentes antes de deduplicar contra el cat\'{a}logo: Lago 7, Chill\'{a}n 5, Cervantes 18, Puerto Montt 4 y Oriente 9. Son observaciones de esa prueba, no conteos permanentes ni una garant\'{i}a de acceso desde GitHub Actions. Puerto Montt publica una ventana m\'{o}vil de 30 d\'{i}as: no se afirma cubrir todo su archivo. Chill\'{a}n utiliza el a\~{n}o expl\'{i}cito de la ficha; Oriente utiliza fechas ISO del JSON-LD y excluye cancelaciones y avisos permanentes.

El conector de tarjetas admite selectores de detalle, campos JSON-LD y enlaces de paginaci\'{o}n configurables. Los detalles fallidos temporalmente, la p\'{e}rdida de campos obligatorios y los ciclos de paginaci\'{o}n marcan una extracci\'{o}n parcial, que no autoriza borrados por ausencia. Esta ampliaci\'{o}n est\'{a} documentada en los JSON ejecutables y \texttt{docs/SOURCES.md}; no modifica los resultados hist\'{o}ricos del inventario Excel.

Las fuentes retiradas se declaran en \texttt{settings.json} mediante \texttt{retired\_source\_names}. Durante la siguiente publicaci\'{o}n se concilian intencionalmente sus eventos extra\'{i}dos con procedencia acreditada. Se conservan publicaciones manuales, eventos suprimidos y eventos con interacciones, aunque pertenezcan a esas fuentes.

\subsection{Validaci\'{o}n de candidatas}

Antes de integrar una fuente, el comando \texttt{validar\_fuentes.bat} revisa el inventario de candidatas sin extraer eventos ni modificar Supabase. Comprueba disponibilidad HTTP, \texttt{robots.txt}, presencia de se\~{n}ales de agenda, fechas, enlaces, pertinencia cultural y cobertura chilena. Sus resultados se guardan en \texttt{data/source\_validation/}; una aprobaci\'{o}n t\'{e}cnica no habilita una fuente autom\'{a}ticamente, pues la configuraci\'{o}n y las pruebas siguen siendo una decisi\'{o}n del equipo.

\section{Flujo de procesamiento}

\subsection{Fase de extracci\'{o}n}

\begin{enumerate}
  \item Se cargan las fuentes habilitadas para el mes actual; FondasChile se omite fuera de septiembre.
  \item Las fuentes se agrupan por dominio. Hasta cuatro dominios se procesan en paralelo, pero cada dominio conserva su propio ritmo.
  \item Cada conector devuelve objetos \texttt{Event} con un esquema com\'{u}n.
  \item Se aplican limpieza inicial, deduplicaci\'{o}n interna y validaci\'{o}n de disponibilidad de fichas.
  \item Cada fuente exitosa o vac\'{i}a de forma v\'{a}lida queda registrada en un checkpoint local.
\end{enumerate}

La fase puede ejecutarse sin IA ni Supabase:

\begin{lstlisting}
python scrape_events.py --phase extract --local-only
\end{lstlisting}

\subsection{Fase de procesamiento y publicaci\'{o}n}

\begin{enumerate}
  \item Se recupera la extracci\'{o}n compatible m\'{a}s reciente desde SQLite.
  \item Se sanea el texto globalmente y se deduplican eventos entre fuentes.
  \item Se aplican valores de ubicaci\'{o}n declarados por fuente y reglas deterministas.
  \item Si Supabase est\'{a} habilitado, se detectan eventos nuevos, modificados, suprimidos o pertenecientes a organizadores bloqueados.
  \item Solo el subconjunto pendiente pasa por OCR, redacci\'{o}n y enriquecimiento de ubicaci\'{o}n.
  \item Se ejecuta el filtro cultural, se descartan fechas inv\'{a}lidas o vencidas y se exportan JSON/CSV.
  \item Se publica de forma at\'{o}mica en Supabase y se reconcilian registros obsoletos de fuentes completas.
\end{enumerate}

\begin{lstlisting}
python scrape_events.py --phase process --supabase
\end{lstlisting}

La separaci\'{o}n de fases permite conservar el trabajo de extracci\'{o}n si se agota una cuota de IA o falla temporalmente el destino remoto.

\section{Modelo can\'{o}nico de evento}

Todo conector entrega el mismo modelo l\'{o}gico. Los campos fundamentales son \texttt{title}, \texttt{start\_date}, \texttt{end\_date}, \texttt{venue}, \texttt{location}, \texttt{commune}, \texttt{region}, \texttt{organizer}, \texttt{categories}, \texttt{source\_url} y \texttt{official\_url}.

Las categor\'{i}as son siempre una lista de disciplinas culturales, no una cadena. Un evento puede pertenecer simult\'{a}neamente a m\'{u}sica y danza. Familiar es un p\'{u}blico; gratuito es una condici\'{o}n de acceso, no una disciplina. En JSON se guarda como arreglo; en CSV se serializa como JSON dentro de una celda; en Supabase se normaliza mediante \texttt{categories} y \texttt{event\_categories}.

La revisi\'{o}n del 27 de octubre incorpora 18 disciplinas can\'{o}nicas y el objeto \texttt{classification}: versi\'{o}n, etiquetas originales, formatos, p\'{u}blicos, programas, evidencia y decisi\'{o}n. Se recalcula incluso para eventos conocidos y checkpoints; cambiar la taxonom\'{i}a no obliga a repetir OCR ni redacci\'{o}n. Gu\'{i}as de librer\'{i}as y fichas de espacios no se convierten en eventos por declarar una vigencia de varios a\~{n}os. Una duraci\'{o}n larga, por s\'{i} sola, no descarta una programaci\'{o}n real.

La ubicaci\'{o}n se resuelve de forma transparente y cada evento incluye:
\begin{itemize}
  \item \texttt{location}: texto can\'{o}nico que nunca queda vac\'{i}o;
  \item \texttt{location\_precision}: direcci\'{o}n, recinto, comuna, regi\'{o}n o modalidad en l\'{i}nea;
  \item \texttt{location\_source}: dato publicado, configuraci\'{o}n de fuente, regla determinista, IA o fallback geogr\'{a}fico.
\end{itemize}

No se inventan direcciones. Cuando la evidencia solo permite identificar una comuna o regi\'{o}n, se conserva exactamente ese nivel y se marca la menor precisi\'{o}n.

\section{Saneamiento, vigencia y filtro cultural}

El saneador com\'{u}n elimina HTML residual, reglas CSS, scripts, shortcodes de WordPress/WPBakery y descripciones desproporcionadas. Esto evita que cambios visuales de un sitio se conviertan en contenido del cat\'{a}logo.

Un evento se conserva solo si tiene fecha de inicio v\'{a}lida y todav\'{i}a est\'{a} vigente. La validaci\'{o}n de URL retira fichas confirmadas con HTTP 404/410 o p\'{a}ginas de error inequ\'{i}vocas; ante timeout, bloqueo temporal o error 5xx el registro se conserva para no borrar informaci\'{o}n por una falla pasajera.

El filtro realiza una comprobaci\'{o}n antes de consumir IA y otra despu\'{e}s del enriquecimiento. Tiene tres resultados: \textit{aceptado}, \textit{revisi\'{o}n} y \textit{excluido}. Se exige contenido cultural verificable; el nombre de la fuente, organizador o recinto no basta. El formato por s\'{i} solo no determina el resultado. Los casos ambiguos se conservan como \texttt{draft}, no publicados. La m\'{u}sica de acompa\~{n}amiento no convierte una clase de fitness en concierto. La auditor\'{i}a queda en \texttt{data/cultural\_filter\_audit.json}.

Ticketplus y las dem\'{a}s fuentes usan primero reglas sobre el contenido. Solo los casos a\'{u}n ambiguos consultan NVIDIA, con categor\'{i}as permitidas y evidencia literal: lotes de 10, hasta 100 candidatos por corrida, cinco minutos adicionales de presupuesto y suspensi\'{o}n tras tres fallos consecutivos. Se mantiene el l\'{i}mite global de 40 RPM y se reutiliza evidencia compatible local o remota. Un fallo no inventa la categor\'{i}a Otros ni impide sincronizar los casos pendientes como borradores.

Esta versi\'{o}n requiere la migraci\'{o}n \path|20261027000100_cultural_classification.sql|. Instalarla no altera filas del cat\'{a}logo. La publicaci\'{o}n at\'{o}mica conserva los metadatos y archiva exclusiones ya existentes sin borrar interacciones. El comando \texttt{python -m tools.reclassify\_catalog} simula el mantenimiento sin NVIDIA; solo \texttt{--apply} habilita escritura despu\'{e}s de revisar la propuesta. Se protegen eventos manuales, supresiones, fuentes inactivas y organizadores bloqueados. El diccionario de base de datos documenta el campo privado \path|event_provenance.classification| y la RPC de mantenimiento.

\section{IA, OCR y control de cuota}

NVIDIA NIM se usa como respaldo, no como requisito de extracci\'{o}n. Las fichas de fuentes con API, JSON-LD, WordPress REST o tarjetas declarativas se leen sin IA, pero sus eventos nuevos o modificados pueden necesitar enriquecimiento posterior. La IA interviene en estos casos:
\begin{itemize}
  \item respaldo de extracci\'{o}n sem\'{a}ntica cuando un conector gen\'{e}rico no encuentra datos estructurados y tiene habilitado ese respaldo;
  \item OCR de afiches con imagen cuyo resultado est\'{a} ausente, pendiente o vencido en cach\'{e}; no depende de que la descripci\'{o}n HTML est\'{e} vac\'{i}a;
  \item redacci\'{o}n editorial de texto p\'{u}blico, preservando el texto de origen para trazabilidad;
  \item resoluci\'{o}n por lotes de ubicaciones incompletas;
  \item clasificaci\'{o}n con evidencia de disciplinas a\'{u}n ambiguas, sin repetir operaciones ya resueltas.
\end{itemize}

El l\'{i}mite global se configura en 40 solicitudes por minuto. Todas las llamadas, incluso las iniciadas por fuentes concurrentes, pasan por el mismo regulador. Las respuestas 429, \texttt{Retry-After} y secuencias de timeouts activan pausas controladas; los pendientes no se pierden, sino que pasan a una cola SQLite para una ejecuci\'{o}n futura.

\subsection{Presupuestos y suspensi\'{o}n controlada}

El timeout de red no es el presupuesto de toda una fase. El OCR tiene, por defecto, 45 segundos de timeout por solicitud, un reintento y hasta 100 segundos de presupuesto por operaci\'{o}n. La etapa admite hasta 100 im\'{a}genes, pero dispone adem\'{a}s de un presupuesto acumulado de 20 minutos. La redacci\'{o}n dispone de otros 20 minutos y la ubicaci\'{o}n de 5 minutos. El tiempo restante recorta la espera y los reintentos de la siguiente operaci\'{o}n.

Cada etapa se suspende despu\'{e}s de tres operaciones consecutivas sin resultado v\'{a}lido. Un resultado v\'{a}lido reinicia el contador; no se cuenta simplemente el total de errores de toda la corrida. En redacci\'{o}n y ubicaci\'{o}n, un lote con resultados v\'{a}lidos parciales conserva los completados y deja el resto pendiente. La suspensi\'{o}n no desactiva autom\'{a}ticamente todas las etapas de IA ni descarta eventos que ya sean v\'{a}lidos.

Los presupuestos suman 45 minutos nominales y reservan margen dentro de los 80 minutos del paso de procesamiento en Actions. No son una garant\'{i}a estricta de duraci\'{o}n ante bloqueos de red o de Supabase. El l\'{i}mite RPM sigue vigente; no se alternan cuentas ni claves para aumentarlo. Las respuestas HTTP 401, 403 y 410 constituyen una indisponibilidad permanente para esa ejecuci\'{o}n y desactivan el respaldo IA global, a diferencia de la suspensi\'{o}n de una sola etapa.

\subsection{Validaci\'{o}n de respuestas y diagn\'{o}stico}

Las solicitudes piden una respuesta sin streaming. Se comprueban por separado la envoltura JSON HTTP, el texto devuelto por el modelo y los campos requeridos. En OCR y redacci\'{o}n se admiten cercos Markdown, pre\'{a}mbulos y una lista unitaria que contenga el objeto esperado; no se inventan campos ni se recuperan subobjetos de estructuras truncadas. Una respuesta marcada como incompleta o filtrada se rechaza antes de actualizar el evento.

Los errores de envoltura informan estado HTTP, tipo de contenido y tama\~{n}o, sin imprimir el cuerpo ni las credenciales. Un \texttt{Read timed out} no demuestra agotamiento de cuota: la evidencia de l\'{i}mite RPM es HTTP 429. La URL cultural identifica el evento afectado; el host del error identifica el servicio con el que fall\'{o} la comunicaci\'{o}n.

El mensaje de suspensi\'{o}n del OCR indica el resto del lote seleccionado, no el tama\~{n}o total de la cola. Una publicaci\'{o}n correcta en Supabase puede coexistir con enriquecimientos pendientes. La suspensi\'{o}n permite continuar hasta la sincronizaci\'{o}n, pero no convierte un fallo real de Supabase en un \'{e}xito ni garantiza la calidad de informaci\'{o}n que no pudo leerse.

Antes de usar IA, Supabase compara URL original y una clave combinada de t\'{i}tulo, fecha y lugar. Si el evento ya existe y no cambi\'{o}, se reutilizan OCR y texto editorial previamente almacenados. Esta deduplicaci\'{o}n reduce costo, tiempo y consumo de cuota.

La RPC privada \texttt{match\_existing\_events(jsonb)} busca por clave externa, URL de extracci\'{o}n o URL oficial. Desde la revisi\'{o}n del 20 de octubre utiliza dos \'{i}ndices B-tree de URL normalizada y ramas de igualdad separadas. Conserva la coincidencia m\'{a}s reciente por clave local y resuelve empates por identificador. El cliente divide las consultas en lotes de entre 1 y 500 candidatos; el workflow utiliza 200. Esto evita respuestas masivas que puedan truncarse por el l\'{i}mite de filas de PostgREST, sin aumentar el l\'{i}mite de NVIDIA.

\section{Estado local, checkpoints y recuperaci\'{o}n}

El archivo \texttt{state/pipeline.sqlite3} conserva datos operativos, no el cat\'{a}logo p\'{u}blico. Incluye checkpoints por fuente, una extracci\'{o}n consolidada, cola de enriquecimiento, cach\'{e} de resultados de IA y de detalles, y el enfriamiento pendiente de NVIDIA. La cach\'{e} HTTP condicional se almacena separadamente en \texttt{.cache/http/}; no debe confundirse con la cola SQLite.

En GitHub Actions, el estado se guarda como artefacto despu\'{e}s de la extracci\'{o}n y nuevamente al finalizar. Una ejecuci\'{o}n siguiente restaura el \'{u}ltimo artefacto disponible. Por ello, si falla la fase de enriquecimiento, no se requiere volver a recorrer todas las p\'{a}ginas: la siguiente corrida retoma los eventos y pendientes conservados.

Las tareas pueden estar pendientes, en proceso, completadas o con error reintentable. Las completadas se reutilizan mientras su entrada y cach\'{e} sigan siendo compatibles. Una corrida terminada inicia un nuevo ciclo de revisi\'{o}n en la siguiente ejecuci\'{o}n; no congela indefinidamente el listado de fuentes. Cambiar los JSON, como al incorporar las cinco fuentes nuevas, invalida la compatibilidad de la extracci\'{o}n consolidada anterior: debe ejecutarse primero la fase de extracci\'{o}n. El workflow ya sigue ese orden. El OCR pendiente solo puede retomarse si se conserva/restaura el estado y el evento sigue siendo elegible.

No deben ejecutarse simult\'{a}neamente dos procesos que compartan el mismo estado local o las mismas credenciales de IA. El workflow usa un grupo de concurrencia para impedir que dos ejecuciones programadas se solapen.

\section{Exportaci\'{o}n y sincronizaci\'{o}n con Supabase}

El respaldo local se escribe en \texttt{data/events.json}, \texttt{data/events.csv}, archivos separados por regi\'{o}n, \texttt{data/source\_metrics.json} y \texttt{data/run\_summary.json}. Al final de cada corrida se informa un total consolidado y duraci\'{o}n completa.

La sincronizaci\'{o}n remota usa la API REST de Supabase con una clave secreta exclusiva del proceso de ingesta. El flujo remoto es:
\begin{enumerate}
  \item transformar eventos en entidades normalizadas: fuentes, organizadores, comunas, categor\'{i}as, eventos, procedencia y medios;
  \item cargar fragmentos en la tabla privada \texttt{catalog\_staging};
  \item ejecutar \texttt{publish\_staged\_catalog(...)} para publicar todo el lote dentro de una transacci\'{o}n;
  \item conciliar ausencias e invocar \texttt{cleanup\_expired\_events()} dentro de esa misma transacci\'{o}n, si la limpieza est\'{a} habilitada;
  \item registrar el resultado de sincronizaci\'{o}n en \texttt{scrape\_runs}.
\end{enumerate}

Las consultas y cargas REST idempotentes reintentan fallas transitorias de red, timeout o disponibilidad temporal. La RPC de publicaci\'{o}n no se repite autom\'{a}ticamente si su respuesta se pierde, porque podr\'{i}a haber finalizado y eliminado el staging; as\'{i} se evita una publicaci\'{o}n ambigua o duplicada.

Los organizadores bloqueados y los eventos suprimidos individualmente se excluyen antes de OCR, redacci\'{o}n y publicaci\'{o}n. De este modo, una solicitud de retiro no se revierte en la siguiente ejecuci\'{o}n.

\subsection{Limpieza protegida y conciliaci\'{o}n}

\texttt{cleanup\_expired\_events()} es una funci\'{o}n PostgreSQL privada que devuelve un \texttt{bigint}; no es un trigger ni un procedimiento invocable con \texttt{CALL}. Usa \texttt{now()} del servidor al inicio de la transacci\'{o}n. Eval\'{u}a tanto eventos manuales como extra\'{i}dos:
\begin{itemize}
  \item con \texttt{end\_at}, elimina cuando el t\'{e}rmino es estrictamente anterior al reloj del servidor;
  \item sin \texttt{end\_at}, elimina cuando el inicio es anterior al comienzo del d\'{i}a actual en \texttt{America/Santiago}; conserva todo el d\'{i}a local de inicio;
  \item conserva eventos suprimidos o con cualquier interacci\'{o}n de usuario, sea positiva o negativa;
  \item conserva fechas sin inicio o con t\'{e}rmino anterior al inicio, para revisi\'{o}n;
  \item elimina por cascada las relaciones de categor\'{i}as, medios y procedencia del evento retirado.
\end{itemize}

La conciliaci\'{o}n por ausencia es otra regla: requiere una fuente autorizada, una fila no vista en la sincronizaci\'{o}n actual, procedencia en \texttt{event\_provenance} y un m\'{e}todo distinto de \texttt{manual}. Tambi\'{e}n protege supresiones e interacciones. Puede retirar una ficha con fecha futura si ya no aparece en una fuente completa; una fuente fallida o parcial no autoriza esa conciliaci\'{o}n.

Las dos rutas utilizan un bloqueo \texttt{SHARE} de \texttt{user\_event\_interactions} para evitar perder se\~{n}ales concurrentes; el tiempo de espera de bloqueos se limita a cinco segundos. Una falla revierte publicaci\'{o}n, relaciones y borrados, manteniendo staging. Las inserciones de interacciones pueden esperar durante esta transacci\'{o}n.

La publicaci\'{o}n devuelve \texttt{removed\_stale} y \texttt{removed\_expired}. El exportador guarda esos contadores en \texttt{scrape\_runs.metadata} cuando marca el \'{e}xito. No son el total restante del cat\'{a}logo. La escritura final de la bit\'{a}cora ocurre despu\'{e}s de la RPC y no revierte una publicaci\'{o}n ya confirmada si falla.

La conservaci\'{o}n de eventos con interacciones es temporal, hasta desacoplar las se\~{n}ales del recomendador. El frontend debe seguir filtrando las fechas: una fila conservada por protecci\'{o}n no necesariamente representa un evento vigente. Las RPC de limpieza y publicaci\'{o}n solo admiten ejecuci\'{o}n con \texttt{service\_role}; \texttt{anon} y \texttt{authenticated} no tienen ese permiso.

\section{Automatizaci\'{o}n con GitHub Actions}

El workflow separa validaci\'{o}n y ejecuci\'{o}n en dos trabajos sobre \texttt{ubuntu-24.04}. El trabajo \texttt{validate} instala dependencias, ejecuta las pruebas de Python y utiliza PostgreSQL 17 temporal para aplicar todas las migraciones y probar las regresiones SQL. El contenedor existe \'{u}nicamente en GitHub Actions: no requiere instalar Docker en el computador local ni contenerizar el scraper.

El trabajo \texttt{scrape} depende del \'{e}xito de \texttt{validate}. Instala Chromium, restaura checkpoints, extrae, conserva un artefacto, enriquece y sincroniza con limpieza protegida. Conserva las copias de estado al finalizar aunque una fase falle. Las credenciales se almacenan como \textit{Repository secrets}: \texttt{SUPABASE\_URL}, \texttt{SUPABASE\_SECRET\_KEY} y \texttt{NVIDIA\_API\_KEY}. La validaci\'{o}n SQL no utiliza estas claves.

El resumen de duraci\'{o}n pertenece al comando que lo genera. Como extracci\'{o}n y procesamiento se ejecutan por separado, el tiempo de una fase no equivale al tiempo completo del workflow. El total de eventos sincronizados tampoco representa necesariamente todas las filas existentes en Supabase: pueden conservarse publicaciones manuales, supresiones o registros protegidos por interacciones.

La programaci\'{o}n vigente es diaria a las 23:37 en la zona \texttt{America/Santiago}, mediante \texttt{37 23 * * *}. El workflow conserva \texttt{workflow\_dispatch} para ejecuci\'{o}n manual. La zona horaria evita ajustar el cron por horario de verano; el programador de GitHub puede retrasar el inicio. Las migraciones remotas se aplican por separado y no en cada ejecuci\'{o}n programada.

\subsection{Cuando una fuente cambia o cae}

\begin{enumerate}
  \item revisar el resumen de fuente y confirmar si fall\'{o}, qued\'{o} parcial o est\'{a} leg\'{i}timamente vac\'{i}a;
  \item comprobar la p\'{a}gina p\'{u}blica y sus t\'{e}rminos de uso antes de cambiar la extracci\'{o}n;
  \item preferir API, JSON-LD o endpoint p\'{u}blico sobre selectores visuales fr\'{a}giles;
  \item actualizar solo el JSON de fuente cuando un conector declarativo sea suficiente;
  \item agregar o corregir pruebas con una muestra representativa antes de habilitar la fuente;
  \item si la fuente falla, mantenerla fuera de la reconciliaci\'{o}n: el pipeline no borra su cat\'{a}logo por una extracci\'{o}n parcial o fallida.
\end{enumerate}

La gu\'{i}a operativa detallada est\'{a} en \texttt{sources/GUIA\_AGREGAR\_Y\_MANTENER\_FUENTES.md}.

\section{Seguridad, l\'{i}mites y consideraciones}

Se consultan \'{u}nicamente recursos p\'{u}blicos. Antes de a\~{n}adir una fuente se deben revisar t\'{e}rminos de uso, \texttt{robots.txt}, condiciones de reutilizaci\'{o}n y frecuencia razonable de consulta. El sistema no debe intentar evadir bloqueos ni acceder a contenido privado.

Las claves secretas de Supabase se usan solamente por el scraper o GitHub Actions; nunca deben llegar al frontend, a archivos versionados ni a logs. El OCR y la redacci\'{o}n automatizada no sustituyen una revisi\'{o}n editorial ni garantizan, por s\'{i} solos, conformidad con pol\'{i}ticas de terceros.
